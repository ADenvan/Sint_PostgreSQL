## Идемпотентные операции в PostgreSQL

**Идемпотентные операции** — это такие операции (запросы, скрипты), которые можно выполнять многократно, и после каждого запуска итоговое состояние базы данных остаётся таким же, как после самого первого успешного запуска. Иными словами, повторный запуск такой операции не создаёт дополнительных побочных эффектов (side effects) и не приводит к ошибкам из-за дублирования данных или нарушения ограничений целостности.

### Почему это важно
В распределённых системах сбои — обычное дело: сеть может потерять пакет, сервер может временно упасть, соединение может разорваться. Клиентские библиотеки и оркестраторы часто реализуют логику повторных попыток (retry), отправляя запрос заново. Если операция не идемпотентна, такой повтор может привести к нежелательным последствиям: созданию дубликатов заказов, двойному списанию средств, рассинхронизации данных или падению скрипта миграции. Идемпотентные операции решают эту проблему: повторная попытка выполнить их либо ничего не меняет, либо меняет данные так, что итоговый результат остаётся строго прежним.

## Примеры идемпотентных операций в PostgreSQL (с уточнениями)

### 1. `INSERT ... ON CONFLICT DO NOTHING`
✅ **Информация верна.** Эта конструкция позволяет вставить строку, но если при этом возникает конфликт с уникальным ограничением (например, по `email` или `id`), операция просто игнорируется. 
```sql
INSERT INTO users (id, email) 
VALUES (1, 'test@example.com') 
ON CONFLICT (email) DO NOTHING;
```
Если выполнить такой запрос несколько раз с одними и теми же данными, таблица не изменится после первого успешного запуска, и ошибка не будет выброшена.
^u1
### 2. `UPSERT` через `ON CONFLICT ... DO UPDATE`

⚠️ **Требует критического уточнения.** В исходном тексте сказано, что эта операция идемпотентна. Это **не всегда так**. Она идемпотентна *только в том случае*, если в блоке `DO UPDATE` вы присваиваете колонкам значения из псевдотаблицы `EXCLUDED` (то есть те же самые данные, которые пытались вставить), а не модифицируете существующие значения.

```sql
-- ✅ ИДЕМПОТЕНТНО:
-- При повторном запуске с теми же данными состояние строки не изменится.
INSERT INTO users (id, name, status) 
VALUES (1, 'Alice', 'active')
ON CONFLICT (id) DO UPDATE 
SET name = EXCLUDED.name, 
    status = EXCLUDED.status;

-- ❌ НЕ ИДЕМПОТЕНТНО:
-- При повторном запуске счётчик будет увеличиваться каждый раз, 
-- а timestamp обновляться, меняя состояние базы данных.
INSERT INTO user_stats (user_id, login_count) 
VALUES (1, 1)
ON CONFLICT (user_id) DO UPDATE 
SET login_count = user_stats.login_count + 1,
    last_seen = NOW();
```
**Вывод для студента:** Чтобы сделать `UPSERT` идемпотентным, убедитесь, что выражения в `DO UPDATE` не зависят от текущего состояния строки (не используют агрегацию, инкремент или функции вроде `NOW()`), либо добавьте условие `WHERE`, проверяющее, что данные действительно изменились: `... DO UPDATE SET ... WHERE users.status IS DISTINCT FROM EXCLUDED.status`.
^0bffcc
### 3. DDL-операции с условиями
✅ **Информация верна, но список можно расширить.** Конструкции с `IF NOT EXISTS` или `OR REPLACE` являются идемпотентными: их можно запускать сколько угодно раз в скриптах миграции, и они не сломаются, если объект уже существует.

Современный список идемпотентных DDL-команд в PostgreSQL:
- `CREATE TABLE IF NOT EXISTS ...`
- `DROP TABLE IF EXISTS ...`
- `CREATE OR REPLACE FUNCTION ...` (Важный нюанс: при замене функции с тем же телом её внутренний `OID` сохраняется, что не ломает зависимые объекты, например, представления или другие функции. Это делает команду безопасной для повторного выполнения).
- `CREATE OR REPLACE VIEW ...`
- `ALTER TABLE table_name ADD COLUMN IF NOT EXISTS column_name data_type` *(доступно начиная с PostgreSQL 11)*.

## Дополнительные паттерны идемпотентности для Data Science и разработки

Как специалисту, вам также полезно знать следующие подходы:

1. **Идемпотентный `DELETE`**  
   Удаление записи по первичному ключу идемпотентно по своей природе. Если строка уже удалена, повторный вызов `DELETE FROM table WHERE id = 1` просто вернёт `0 rows affected` и не вызовет ошибки.

2. **Паттерн "Ключ идемпотентности" (Idempotency Key)**  
   Для сложных бизнес-операций (например, начисление бонусов), которые нельзя сделать идемпотентными на уровне чистого синтаксиса SQL, создают отдельную таблицу:
   ```sql
   CREATE TABLE idempotency_keys (
       key_hash TEXT PRIMARY KEY,
       response_data JSONB,
       created_at TIMESTAMP DEFAULT NOW()
   );
   ```
   Перед выполнением операции скрипт пытается вставить хеш запроса в эту таблицу. Если возникает конфликт (`ON CONFLICT DO NOTHING` или `DO UPDATE`), система понимает, что операция уже выполнялась, и возвращает сохранённый результат, не выполняя бизнес-логику повторно.

3. **Использование CTE (Common Table Expressions) для атомарности**  
   Иногда идемпотентность требует проверки состояния перед действием. В PostgreSQL это можно сделать атомарно в одном запросе через `WITH`, что исключает race conditions (состояния гонки) при параллельных повторных запросах.
